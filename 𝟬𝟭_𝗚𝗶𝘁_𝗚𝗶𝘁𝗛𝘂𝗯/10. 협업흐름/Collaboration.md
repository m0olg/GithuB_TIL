## 협업 흐름

<br>


# 01 Git 협업이란?

지금까지 정리한 <mark>commit, branch, remote, merge 같은 명령어들을 **여러 명이 함께 일할 때 어떤 순서와 규칙으로 쓰는지**가 협업 흐름</mark>임

명령어를 아는 것과 팀에서 잘 쓰는 것은 다른 문제 \
같은 저장소에서 여러 사람이 동시에 작업하면 결국 서로의 코드가 부딪히게 되는데 이걸 줄이려면 **브랜치를 나누는 방식, 커밋 메시지를 쓰는 방식, 코드를 합치는 절차**를 미리 약속해두어야 함 !!

이 문서에서는 크게 네 가지를 다룸
- 저장소에 접근하는 방식 (같은 저장소에서 작업 / Fork해서 작업)
- 브랜치 전략
- 커밋 컨벤션
- 이슈와 PR 작성 규칙


<br>

# 02 협업 방식 두 가지

## ① 같은 저장소에서 작업하기

동아리나 회사처럼 팀원이 모두 저장소에 **쓰기 권한**이 있는 경우의 방식임 \
한 저장소를 함께 `clone`해서 쓰고 각자 브랜치를 만들어 작업한 뒤 PR로 합침

흐름은 이전 문서들에서 본 것과 같음


> 최신 main 받기 → 작업 브랜치 생성 → 작업 및 Commit → Push → PR 생성 → 코드 리뷰 → Merge


소규모 팀에서는 대부분 이 방식을 씀




## ② Fork해서 작업하기

오픈소스처럼 **내게 쓰기 권한이 없는 저장소**에 기여할 때 쓰는 방식임. 원본 저장소에 바로 브랜치를 만들 수 없으니, 먼저 저장소를 통째로 내 계정으로 복사해옴. 이것이 **Fork**임

흐름은 다음과 같음

1. GitHub에서 원본 저장소의 `Fork` 버튼을 눌러 내 계정에 복사본을 만듦
2. 내 복사본을 내 컴퓨터로 `clone`함
3. 브랜치를 만들어서 작업하고 내 복사본에 Push함
4. 내 복사본에서 **원본 저장소로** PR을 보냄
5. 원본 저장소의 관리자가 리뷰한 뒤 Merge함

Fork를 쓸 때 꼭 알아야 할 것이 **upstream**임. 내 복사본은 Fork한 시점에서 멈춰 있고 원본은 계속 바뀌기 때문에, 원본의 최신 내용을 따로 가져와야 함. 이때 원본 저장소를 `upstream`이라는 이름으로 등록해둠

```bash
git remote add upstream https://github.com/원본계정/저장소.git
git fetch upstream
git merge upstream/main
```

`origin`은 내 복사본, `upstream`은 원본이라고 구분하면 됨. 작업을 시작하기 전에 upstream의 최신 내용을 먼저 받아두면 충돌을 많이 줄일 수 있음

# 03 브랜치 전략

팀에서 브랜치를 **어떤 이름으로, 어떤 기준으로 만들고 합칠지** 정해둔 규칙을 브랜치 전략이라고 함. 정해두지 않으면 사람마다 다르게 쓰게 되고, 어떤 브랜치가 최신인지 알기 어려워짐

*대표적으로 두 가지가 많이 쓰임*




## ① GitHub Flow

가장 단순한 방식임. 브랜치가 `main` 하나와 작업용 브랜치뿐임

- `main` : 항상 배포할 수 있는 상태를 유지하는 브랜치
- `feature/...` : 기능 하나를 작업하고 PR로 `main`에 합치는 브랜치

작업이 끝나면 PR을 통해 `main`에 바로 Merge하고, 합쳐진 작업 브랜치는 삭제함

구조가 단순해서 배우기 쉽고, 소규모 팀이나 자주 배포하는 프로젝트에 잘 맞음. 학생 프로젝트나 동아리 팀 프로젝트라면 이 방식으로 충분한 경우가 많음




## ② Git Flow

브랜치를 역할별로 세분화한 방식임. 정해진 일정에 맞춰 버전을 배포하는 프로젝트에 어울림

- `main` : 실제 배포된 안정 버전
- `develop` : 다음 배포를 위해 개발 내용을 모아두는 브랜치
- `feature/...` : 기능 개발. `develop`에서 만들어서 `develop`으로 합침
- `release/...` : 배포 직전에 마지막으로 점검하고 버그를 잡는 브랜치
- `hotfix/...` : 배포된 버전의 긴급 버그를 수정하는 브랜치. `main`에서 만들어서 `main`과 `develop` 모두에 반영함

역할이 명확한 대신 브랜치가 많아서 관리가 복잡함. 앱처럼 심사나 버전 배포 과정이 있는 프로젝트에서 쓰기도 하지만, 규모가 작으면 오히려 번거로울 수 있음




## ③ 브랜치 이름 규칙

전략과 상관없이 이름도 통일해두면 좋음. 보통 `종류/작업내용` 형태로 씀

- `feature/login` : 새 기능
- `fix/button-color` : 버그 수정
- `docs/readme` : 문서 수정
- `refactor/network-layer` : 코드 정리

이름만 보고도 무슨 작업인지 알 수 있어서, 브랜치 목록을 볼 때나 PR을 리뷰할 때 훨씬 편함. 띄어쓰기 대신 `-`를 쓰고, 영어 소문자로 통일하는 것이 일반적임

# 04 커밋 컨벤션

커밋 메시지도 팀 전체가 같은 형식으로 쓰면 기록을 읽기 훨씬 편해짐. 가장 널리 쓰이는 방식은 **앞에 커밋의 종류를 붙이는 것**임

```text
feat: 로그인 화면 추가
fix: 로그인 버튼이 눌리지 않는 오류 수정
```

`종류: 설명` 형태이고, 콜론 뒤에 한 칸 띄어서 씀




## ① 자주 쓰는 종류

- `feat` : 새로운 기능 추가
- `fix` : 버그 수정
- `docs` : 문서 수정 (README 등)
- `style` : 코드 동작과 상관없는 포맷 수정 (띄어쓰기, 세미콜론 등)
- `refactor` : 기능 변경 없이 코드 구조를 개선
- `test` : 테스트 코드 추가 및 수정
- `chore` : 빌드 설정, 패키지 관리 등 기타 작업

팀마다 종류를 더하거나 빼기도 하니, 정확한 목록은 팀 규칙을 따르면 됨




## ② 좋은 커밋 메시지

- **한 커밋에는 하나의 작업만** 담음. "로그인 추가하고 버튼 색상도 바꿈"처럼 두 가지가 섞이면 되돌리거나 찾기 어려움
- 제목은 **무엇을 했는지** 짧고 분명하게 씀. "수정", "작업 중" 같은 메시지는 나중에 보면 아무것도 알 수 없음
- 제목은 보통 50자 안팎으로 쓰고, 마침표는 붙이지 않음
- 설명이 더 필요하면 제목 아래에 한 줄을 띄우고 **왜 그렇게 바꿨는지**를 본문에 적음

커밋 메시지는 "무엇을 바꿨는가"보다 **"왜 바꿨는가"**가 잘 드러날수록 좋은 기록이 됨


<br>

# 05 이슈(Issue) 활용하기

Issue는 GitHub에서 **할 일, 버그, 아이디어를 기록하고 관리하는 게시판**임. 작업을 시작하기 전에 이슈부터 만들어두면 누가 무엇을 하고 있는지 팀원들이 한눈에 알 수 있음

- 제목과 설명에 해야 할 일이나 문제 상황을 적음
- `Assignees`로 담당자를 지정함
- `Labels`로 `bug`, `feature`, `documentation` 같은 분류를 붙임
- 각 이슈에는 `#12`처럼 번호가 자동으로 붙음

이 번호를 PR이나 커밋 메시지에서 활용할 수 있음. 예를 들어 PR 설명에 `Closes #12`라고 적어두면 **그 PR이 Merge될 때 12번 이슈가 자동으로 닫힘**. `Fixes`, `Resolves`도 같은 역할을 함

이렇게 이슈 → 브랜치 → PR로 이어지게 관리하면, 나중에 "이 코드는 왜 바뀌었지?" 할 때 이슈를 따라가며 배경을 찾을 수 있음



<br>
<br>



# 06 좋은 PR 작성하기

PR은 코드뿐 아니라 **리뷰하는 사람에게 보내는 설명서**이기도 함. 어떤 작업인지 알려주지 않으면 리뷰어가 코드를 하나하나 읽으면서 추측해야 해서 시간이 오래 걸림




## ① PR에 적으면 좋은 내용

- **무엇을 했는지** : 작업 내용을 요약함
- **왜 했는지** : 관련된 이슈 번호나 배경을 적음
- **어떻게 확인했는지** : 테스트한 방법이나 확인한 내용을 적음
- **화면 변경이 있다면** : 스크린샷을 첨부함
- **리뷰어가 특히 봐줬으면 하는 부분**

매번 같은 형식으로 쓰고 싶다면 **PR 템플릿**을 만들어둘 수 있음. 저장소에 `.github/pull_request_template.md` 파일을 만들어두면 PR을 만들 때 그 내용이 자동으로 채워짐. 이슈도 `.github/ISSUE_TEMPLATE/` 폴더에 템플릿을 만들 수 있음




## ② PR 크기는 작게

PR이 너무 크면 리뷰하는 사람이 지치고, 문제를 놓칠 가능성도 커짐. **하나의 PR에는 하나의 목적만** 담고, 변경 규모가 크면 나눠서 올리는 것이 좋음

중간에 작업이 끝나지 않았는데 미리 공유하고 싶다면 **Draft PR**로 올릴 수 있음. Draft 상태에서는 Merge가 막혀 있어서, 작업 중이라는 표시를 하면서 피드백을 먼저 받을 수 있음




## ③ 코드 리뷰할 때 마음가짐

- 사람이 아니라 **코드**에 대해 이야기함
- 문제를 지적할 때는 이유와 대안을 함께 적으면 좋음
- 칭찬할 부분도 남기면 분위기가 훨씬 좋아짐
- 리뷰를 받는 쪽도 지적을 개인적으로 받아들이지 않고, 코드를 더 좋게 만드는 과정으로 생각함

리뷰의 목적은 흠을 찾는 것이 아니라 **팀 전체가 같은 수준의 코드를 유지하는 것**임

# 07 협업할 때 지켜야 할 습관

### ① 작업 시작 전에 항상 최신 코드 받기

남이 이미 고친 부분을 모르고 같은 곳을 작업하면 충돌이 나기 쉬움. 브랜치를 만들기 전에 `main`을 최신으로 맞추고, 작업 중에도 가끔 `main`의 변경 사항을 가져오는 것이 좋음




### ② 작업은 작게, 자주 커밋하고 Push하기

한 번에 크게 작업하면 충돌이 났을 때 해결하기도 어렵고 문제의 원인을 찾기도 어려움. 작은 단위로 자주 올릴수록 서로의 작업이 덜 부딪힘




### ③ main에 직접 Push하지 않기

항상 브랜치를 만들고 PR을 통해 합침. GitHub의 **Branch Protection** 기능을 쓰면 `main`에 직접 Push하는 것을 막고, 리뷰 승인을 받아야만 Merge할 수 있도록 강제할 수 있음




### ④ 충돌은 PR을 올리기 전에 내 쪽에서 해결하기

PR을 올리기 전에 최신 `main`을 내 브랜치에 반영해서 충돌을 미리 해결해두는 것이 예의임. 리뷰어가 충돌 상태의 PR을 받으면 확인하기가 어려움




### ⑤ 팀 규칙은 문서로 남기기

브랜치 전략, 커밋 컨벤션, PR 규칙은 말로만 정하면 금방 잊힘. `README`나 `CONTRIBUTING.md` 같은 문서에 적어두면 새로 들어온 팀원도 규칙을 바로 확인할 수 있음

# 08 협업 전체 흐름

이슈를 만들어서 작업을 시작하고 Merge까지 가는 전체 과정은 다음과 같음

먼저 이슈를 만들어서 할 일을 정리하고 담당자를 지정함 \
그다음 최신 `main`을 받아서 `feature/login` 같은 작업 브랜치를 만들고 \
커밋 컨벤션에 맞춰 작업 내용을 Commit함 \
작업하는 동안 `main`이 바뀌었다면 최신 내용을 반영해서 충돌을 미리 해결해둠

작업이 끝나면 GitHub에 Push하고 \
PR 설명에 `Closes #이슈번호`를 적어서 Pull Request를 생성 \
이후 코드 리뷰를 받고 수정할 부분이 있으면 반영한 뒤 승인을 받으면 Merge \
마지막으로 다 쓴 작업 브랜치를 삭제하면 연결해둔 이슈도 자동으로 닫힘

Fork 방식이라면 맨 앞에 Fork와 upstream 설정이 추가되고 PR을 원본 저장소로 보낸다는 점만 다름

# 09 정리

- Git 협업은 여러 명이 같은 저장소를 안전하게 쓰기 위한 브랜치, 커밋, PR 규칙을 정하는 것임
- 쓰기 권한이 있으면 같은 저장소에서 브랜치를 만들어 작업하고, 없으면 Fork해서 PR을 보냄
- Fork한 저장소는 원본을 `upstream`으로 등록해서 최신 내용을 따로 받아와야 함
- GitHub Flow는 `main`과 작업 브랜치만 쓰는 단순한 방식이고, Git Flow는 `develop`, `release`, `hotfix`까지 쓰는 세분화된 방식임
- 소규모 팀이나 학생 프로젝트에는 보통 GitHub Flow로 충분함
- 브랜치 이름은 `feature/login`, `fix/button`처럼 종류와 작업 내용을 함께 적음
- 커밋 메시지는 `feat: 설명`처럼 종류를 앞에 붙이고, 한 커밋에는 하나의 작업만 담음
- 좋은 커밋 메시지는 무엇을 바꿨는지보다 왜 바꿨는지가 드러남
- Issue로 작업을 기록하고 PR에 `Closes #번호`를 적으면 Merge될 때 이슈가 자동으로 닫힘
- PR은 작게 하나의 목적만 담고 무엇을 왜 했는지 설명을 적어야 함
- 작업이 덜 끝났으면 Draft PR로 올려서 먼저 피드백을 받을 수 있음
- `main`에는 직접 Push하지 않고, 항상 PR과 코드 리뷰를 거쳐 합침
- 작업 전에 최신 코드를 받고 충돌은 PR을 올리기 전에 내 쪽에서 해결함
