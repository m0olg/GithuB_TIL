# 01 reflog란?

→ Reflog는 **HEAD가 어디를 가리켰는지 시간 순서대로 기록해둔 로컬 이력**

`git log`는 현재 브랜치에서 이어지는 커밋 기록을 보여주지만, Reflog는 **내가 어떤 작업을 해왔는지의 발자취**를 보여줌. 커밋을 만들고, 브랜치를 옮기고, Reset이나 Rebase를 할 때마다 HEAD의 위치가 바뀌는데 그 변화를 전부 적어두는 것임

그래서 `reset --hard`로 커밋을 날려버렸거나, 브랜치를 실수로 지웠을 때도 Reflog를 보면 **사라진 줄 알았던 커밋의 위치를 찾을 수 있음**

Git에서 거의 유일한 "되돌리기의 되돌리기" 도구라고 생각하면 편함

<br>
<br>

# 02 reflog를 사용하는 이유

05번 문서에서 `reset`은 커밋을 되돌리는 명령어라고 했는데, 특히 `--hard` 옵션은 잘못 쓰면 작업 내용이 통째로 사라진 것처럼 보임

하지만 사실 Git은 커밋을 바로 지우지 않음. 브랜치에서 연결이 끊겼을 뿐 **커밋 자체는 한동안 저장소에 남아 있고** 그 위치를 알려주는 것이 Reflog임

### Reflog가 도움이 되는 상황 !

- `git reset --hard`로 커밋을 날려버렸을 때
- 브랜치를 삭제했는데 아직 Merge하지 않은 작업이 있었을 때
- Rebase를 했는데 결과가 이상해서 이전으로 돌아가고 싶을 때
- `commit --amend`를 잘못해서 원래 커밋이 필요할 때
- Detached HEAD 상태에서 커밋했다가 브랜치를 이동해서 찾지 못할 때

처음 Git을 쓸 때는 큰 사고가 나면 막막하지만, Reflog를 알고 있으면 **대부분의 실수는 복구할 수 있다는 안정감**이 생김

<br>
<br>



# 03 reflog 확인하기

```bash
git reflog
```

실행하면 가장 최근에 한 작업이 맨 위에 표시됨

```text
어쩌구 HEAD@{0}: reset: moving to HEAD~2
블라블라 HEAD@{1}: commit: 로그인 버튼 추가
저쩌구 HEAD@{2}: commit: 로그인 화면 구현
djWJfxlql HEAD@{3}: checkout: moving from main to feature/login
```

각 줄은 왼쪽부터 **그때의 커밋 해시, `HEAD@{번호}`, 어떤 작업이었는지, 설명** 순서임

- `HEAD@{0}` : 가장 최근 상태. 숫자가 커질수록 과거임
- 커밋, 브랜치 이동, Reset, Rebase, Merge 같은 작업이 모두 기록됨

위 예시를 보면 맨 위에서 `reset`으로 커밋 두 개가 사라졌지만, 바로 아래 `HEAD@{1}`에 로그인 버튼을 추가한 커밋이 그대로 남아 있음. **복구하려면 이 지점으로 돌아가면 됨**

특정 브랜치의 기록만 보고 싶다면 `git reflog show 브랜치명`을 사용함


<br>

# 04 복구하는 방법

복구는 기본적으로 두 단계임. Reflog에서 돌아가고 싶은 시점을 찾고, 그 시점으로 이동함

돌아가는 방법은 두 가지가 있음

### ① 현재 브랜치를 그 시점으로 되돌리기
```bash
git reset --hard HEAD@{1}
```

브랜치의 위치 자체를 해당 시점으로 옮김. 가장 간단하지만 현재 작업 폴더의 변경 사항이 덮어써지므로, 커밋하지 않은 내용이 있다면 먼저 확인해야 함

### ② 그 시점에서 새 브랜치 만들기

```bash
git branch recovered e4f5g6h
```

해시를 직접 지정해서 새 브랜치를 만듦. 현재 브랜치는 건드리지 않고 사라졌던 커밋을 안전하게 살려둘 수 있음. 어디로 돌아가야 할지 확신이 없을 때는 이쪽이 더 안전함

처음에는 ②번으로 일단 살려놓고, 내용을 확인한 뒤에 필요한 방식으로 합치는 것을 추천함


<br>
<br>


# 05 상황별 복구 방법

## ① reset --hard로 커밋을 날렸을 때

가장 흔한 경우임. `git reflog`로 reset 직전 커밋을 찾아서 `git reset --hard 해시` 또는 `HEAD@{번호}`로 돌아가면 됨

바로 직전에 한 reset이라면 `ORIG_HEAD`라는 이름표를 쓰는 방법도 있음. Git은 Reset, Merge, Rebase처럼 HEAD를 크게 움직이는 작업 직전의 위치를 `ORIG_HEAD`에 저장해둠

```bash
git reset --hard ORIG_HEAD
```

reflog를 뒤질 필요 없이 한 번에 직전 상태로 돌아갈 수 있어서 편함. 다만 이후에 다른 작업을 하면 덮어써지므로 **바로 직후에만 유효함**




## ② 브랜치를 실수로 삭제했을 때

`git branch -D`로 브랜치를 지워도 커밋은 남아 있음. `git reflog`에서 삭제한 브랜치의 마지막 커밋을 찾아 같은 이름으로 다시 만들면 됨

```bash
git branch feature/login e4f5g6h
```

브랜치가 사라진 직전에 `checkout: moving from feature/login to main` 같은 기록이 있을 테니, 그 바로 앞의 커밋 해시를 찾으면 됨




## ③ rebase를 취소하고 싶을 때

07번 문서에서 이미 끝난 Rebase는 `reflog`로 되돌린다고 했음. `git reflog`에서 `rebase (start)` 기록의 **바로 아래 줄**이 Rebase를 시작하기 직전의 상태임

그 줄의 `HEAD@{번호}`로 `git reset --hard`를 하면 Rebase 전으로 돌아감. 바로 직후라면 `ORIG_HEAD`로도 가능함




## ④ commit --amend를 잘못했을 때

`--amend`는 직전 커밋을 새 커밋으로 바꿔치기하는 작업이라, 원래 커밋이 사라진 것처럼 보임. 하지만 원래 커밋도 reflog에 남아 있으므로 그 해시로 돌아가면 됨




## ⑤ Detached HEAD에서 만든 커밋을 잃어버렸을 때

특정 커밋으로 이동한 상태(Detached HEAD)에서 작업하고 커밋한 뒤, 브랜치를 만들지 않고 다른 곳으로 이동하면 그 커밋은 어떤 브랜치에도 속하지 않게 됨

이때도 reflog에는 기록이 남아 있으므로 해시를 찾아서 새 브랜치로 살려주면 됨

# 06 git log와 reflog의 차이

두 명령어는 비슷해 보이지만 보여주는 대상이 다름

- `git log` : 현재 브랜치에서 **이어지는 커밋의 역사**를 보여줌. 브랜치에서 끊어진 커밋은 나오지 않음
- `git reflog` : **내가 한 작업의 이력**을 보여줌. 브랜치에서 사라진 커밋도 나옴

또 `git log`는 저장소를 공유하면 팀원도 같은 내용을 볼 수 있지만, Reflog는 **내 컴퓨터에만 있는 개인 기록**임. 그래서 팀원이 내 reflog를 볼 수는 없음



<br>
<br>



# 07 reflog 사용할 때 주의할 점

### ① 로컬에만 존재함

Reflog는 GitHub에 올라가지 않음. 내 컴퓨터에서 한 작업만 기록되고, 저장소를 새로 `clone`하면 reflog는 비어 있음. 다른 컴퓨터에서 한 작업이나 원격 저장소에서 지워진 커밋은 이 방법으로 찾을 수 없음




### ② 영원히 남아 있지 않음

Reflog 기록은 기본적으로 **일정 기간이 지나면 정리됨**. 보통 연결된 커밋은 90일, 연결이 끊긴 커밋은 30일 정도 보관됨. 그래서 "예전에 지운 것 같은데…" 하고 한참 뒤에 찾으면 이미 없을 수 있음. 실수했다면 가능한 한 빨리 복구하는 것이 좋음




### ③ 커밋하지 않은 변경 사항은 복구할 수 없음

Reflog는 **커밋을 기록하는 도구**임. 한 번도 커밋하지 않은 채로 `reset --hard`나 `git restore`로 날려버린 작업은 Reflog에도 남아 있지 않아서 복구하기 어려움

그래서 작업 중간중간 커밋해두거나 Stash를 활용하는 습관이 중요함. 임시 커밋이라도 해두면 reflog가 지켜줌




### ④ 복구 전에 현재 상태 확인하기

`git reset --hard`로 복구하면 현재 작업 폴더가 덮어써짐. 복구하기 전에 `git status`로 저장하지 않은 변경 사항이 있는지 확인하고, 불안하다면 앞에서 설명한 **새 브랜치로 살려놓는 방법**을 먼저 쓰는 것이 안전함

# 08 정리

- Reflog는 HEAD가 이동한 모든 기록을 시간 순서대로 저장해둔 로컬 이력임
- `git reset --hard`나 브랜치 삭제로 사라진 것처럼 보이는 커밋도 Reflog에서 찾을 수 있음
- `git reflog`로 확인하고, `HEAD@{번호}`로 시점을 지정함
- 복구는 `git reset --hard HEAD@{번호}`로 되돌리거나, `git branch 이름 해시`로 새 브랜치를 만들어 살려놓는 두 가지 방법이 있음
- 확신이 없을 때는 현재 브랜치를 건드리지 않는 새 브랜치 방식이 더 안전함
- 바로 직전의 Reset, Merge, Rebase는 `ORIG_HEAD`로 한 번에 되돌릴 수 있음
- `git log`는 브랜치에 이어진 커밋 역사, `git reflog`는 내가 한 작업의 이력을 보여줌
- Reflog는 내 컴퓨터에만 있고 GitHub에는 올라가지 않음
- 기록은 보통 30~90일 정도 지나면 정리되므로 실수했다면 빨리 복구해야 함
- 한 번도 커밋하지 않은 변경 사항은 Reflog로도 복구할 수 없으므로 작업 중간에 커밋하거나 Stash를 활용해야 함
