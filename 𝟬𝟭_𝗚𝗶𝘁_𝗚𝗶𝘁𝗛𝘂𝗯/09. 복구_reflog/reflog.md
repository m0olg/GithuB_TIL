# 01 reflog란?

→ Reflog는 **HEAD가 어디를 가리켰는지 시간 순서대로 기록해둔 로컬 이력**

`git log`는 현재 브랜치에서 이어지는 커밋 기록을 보여주지만, Reflog는 **내가 어떤 작업을 해왔는지의 발자취**를 보여줌. 커밋을 만들고, 브랜치를 옮기고, Reset이나 Rebase를 할 때마다 HEAD의 위치가 바뀌는데 그 변화를 전부 적어두는 것임

그래서 `reset --hard`로 커밋을 날려버렸거나, 브랜치를 실수로 지웠을 때도 Reflog를 보면 **사라진 줄 알았던 커밋의 위치를 찾을 수 있음**

Git에서 거의 유일한 "되돌리기의 되돌리기" 도구라고 생각하면 편함

<br>
<br>

# 02 reflog를 사용하는 이유

05번 문서에서 `reset`은 커밋을 되돌리는 명령어라고 했는데, 특히 `--hard` 옵션은 잘못 쓰면 작업 내용이 통째로 사라진 것처럼 보임

하지만 사실 Git은 커밋을 바로 지우지 않음. 브랜치에서 연결이 끊겼을 뿐 **커밋 자체는 한동안 저장소에 남아 있고** 그 위치를 알려주는 것이 Reflog임

### Reflog가 도움이 되는 상황 !

- `git reset --hard`로 커밋을 날려버렸을 때
- 브랜치를 삭제했는데 아직 Merge하지 않은 작업이 있었을 때
- Rebase를 했는데 결과가 이상해서 이전으로 돌아가고 싶을 때
- `commit --amend`를 잘못해서 원래 커밋이 필요할 때
- Detached HEAD 상태에서 커밋했다가 브랜치를 이동해서 찾지 못할 때

처음 Git을 쓸 때는 큰 사고가 나면 막막하지만, Reflog를 알고 있으면 **대부분의 실수는 복구할 수 있다는 안정감**이 생김

# 03 reflog 확인하기

```bash
git reflog
```

실행하면 가장 최근에 한 작업이 맨 위에 표시됨

```text
어쩌구 HEAD@{0}: reset: moving to HEAD~2
블라블라 HEAD@{1}: commit: 로그인 버튼 추가
저쩌구 HEAD@{2}: commit: 로그인 화면 구현
djWJfxlql HEAD@{3}: checkout: moving from main to feature/login
```

각 줄은 왼쪽부터 **그때의 커밋 해시, `HEAD@{번호}`, 어떤 작업이었는지, 설명** 순서임

- `HEAD@{0}` : 가장 최근 상태. 숫자가 커질수록 과거임
- 커밋, 브랜치 이동, Reset, Rebase, Merge 같은 작업이 모두 기록됨

위 예시를 보면 맨 위에서 `reset`으로 커밋 두 개가 사라졌지만, 바로 아래 `HEAD@{1}`에 로그인 버튼을 추가한 커밋이 그대로 남아 있음. **복구하려면 이 지점으로 돌아가면 됨**

특정 브랜치의 기록만 보고 싶다면 `git reflog show 브랜치명`을 사용함

# 04 복구하는 방법

복구는 기본적으로 두 단계임. Reflog에서 돌아가고 싶은 시점을 찾고, 그 시점으로 이동함

돌아가는 방법은 두 가지가 있음

### ① 현재 브랜치를 그 시점으로 되돌리기
```bash
git reset --hard HEAD@{1}
```

브랜치의 위치 자체를 해당 시점으로 옮김. 가장 간단하지만 현재 작업 폴더의 변경 사항이 덮어써지므로, 커밋하지 않은 내용이 있다면 먼저 확인해야 함

### ② 그 시점에서 새 브랜치 만들기

```bash
git branch recovered e4f5g6h
```

해시를 직접 지정해서 새 브랜치를 만듦. 현재 브랜치는 건드리지 않고 사라졌던 커밋을 안전하게 살려둘 수 있음. 어디로 돌아가야 할지 확신이 없을 때는 이쪽이 더 안전함

처음에는 ②번으로 일단 살려놓고, 내용을 확인한 뒤에 필요한 방식으로 합치는 것을 추천함
